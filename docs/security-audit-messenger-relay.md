# Аудит безопасности: messenger-relay (MVP)

Внутренний adversarial-аудит MVP-релея (`messenger/`) против модели угроз,
заявленной в [`anonymous-vps-e2ee-messenger.md`](anonymous-vps-e2ee-messenger.md),
§8:

> Атакующий получает root VPS, disk snapshot, RAM dump, database, logs,
> TLS certificate и исходный код backend. Даже после этого он не должен
> восстановить историю сообщений.

Задача аудита — не «похвалить», а **оспорить**: где текущие утверждения
README не выдерживают этой модели и как правильнее. Ссылки на код даны на
момент коммита `30b796d`.

## TL;DR

Реализация корректно защищает **содержимое** переписки (E2EE-конверты, сервер
их не разбирает, жёсткий TTL). Но два заголовочных claim'а README ложны под
заявленной моделью, а дефолты приводят к OOM на рекомендованном VPS:

1. **«Ничего связанное с сообщениями не пишется на диск»** — неверно:
   swap и core dump выносят ciphertext, TLS-ключ и TLS-секреты на диск.
   (F1, критично)
2. **«Zero-knowledge relay»** — неверно: сервер знает полный социальный граф
   (кто→кому→когда→как часто→какого размера). Это «zero-**content**-knowledge»,
   не zero-knowledge. (F3, высокая)
3. **«restart = crypto-erasure»** — неверно: drop из HashMap и выход процесса
   не зануляют RAM; RAM dump (в модели угроз!) восстанавливает байты. (F2)
4. **Дефолтные лимиты OOM'ят рекомендованный 1.5 GB VPS** ровно из документа:
   32 × 512 × 64 KiB = 1.0 GiB очереди. (F6, высокая)

Ниже — по каждому: **claim, который ломается → доказательство → как лучше**.

---

## Что реализовано правильно (чтобы критике можно было доверять)

- `verify_strict` для Ed25519 (`auth.rs:84`) — отсекает malleability подписей.
- Сравнение invite-токена в constant time (`auth.rs:89`, `ct_eq`).
- TTL жёстко ограничен 20 минутами **в коде**, env не может это превысить
  (`config.rs:44`, `clamp(MIN_TTL, MAX_TTL)`).
- Очередь ограничена на устройство, число устройств ограничено.
- Одно соединение на устройство с вытеснением (`state.rs`, `Online::connect`).
- Единый opaque-ответ на все ошибки аутентификации (`api.rs`, `From<AuthError>`),
  без утечки причины.
- Replay-cache отсекает повтор подписи в окне (`auth.rs:107`).

Эти механизмы верны. Проблема не в них, а в **claim'ах вокруг disk/RAM/metadata**.

---

## F1 (критично). «Ничего не пишется на диск» ломается swap'ом и core dump

**Claim README:** «Очередь сообщений живёт только в RAM… ничего
message-related не касается диска, disk snapshot не даёт данных сообщений».

**Доказательство ложности.** В коде нет ни одного из барьеров, которые не
дают ядру и рантайму вынести память процесса на диск:

```
$ grep -riE 'mlock|zeroize|dumpable|rlimit|madvise|memlock' src/ Cargo.toml
НЕТ ни одного упоминания
```

Следствия под моделью «disk snapshot»:

- **Swap.** При нехватке RAM ядро страницирует анонимную память процесса в
  swap. Туда попадают: ciphertext из очереди, дешифрованные TLS-записи,
  session keys и — при on-box TLS (`rustls`) — приватный TLS-ключ,
  загруженный в память. На диске оказывается то, что README обещает там
  никогда не держать, причём **дольше 20-минутного TTL** (swap живёт до
  перезаписи).
- **Core dump.** Паника или сегфолт при дефолтном `RLIMIT_CORE` пишут дамп
  всей памяти процесса на диск: ciphertext + TLS private key.
- **tmpfs vs диск.** `MSGR_DB_PATH` и рабочая директория по умолчанию — на
  обычном диске.

**Как лучше (и почему это доказуемо закрывает ветку disk-snapshot):**

1. `mlockall(MCL_CURRENT | MCL_FUTURE)` на старте — залоченные страницы ядро
   **не имеет права** свопить (man mlockall). Требует `CAP_IPC_LOCK` или
   поднятого `RLIMIT_MEMLOCK` (в systemd-юните `LimitMEMLOCK=infinity`).
2. Запретить core dump процессу: `setrlimit(RLIMIT_CORE, 0)` +
   `prctl(PR_SET_DUMPABLE, 0)` (последнее также запрещает `ptrace` от
   не-root процессов).
3. Деплой: `swapoff -a` **или** зашифрованный swap (`cryptsetup`+random key
   на каждый boot); systemd — `MemoryDenyWriteExecute=yes`, working dir на
   `tmpfs`.
4. Не терминировать TLS на том же процессе, где лежит ciphertext, если ключ
   нельзя защитить (см. F… ниже про TLS-ключ).

Только после (1)+(2)+(3) утверждение «disk snapshot не содержит сообщений»
становится истинным. Сейчас оно опровергается одним `free -m` под нагрузкой.

## F2 (высокая). «restart = crypto-erasure» — терминологически ложно

**Claim README:** «Рестарт = гарантированная crypto-erasure очереди»; раздел
§11 документа требует именно crypto-erasure.

**Доказательство ложности.** `MessageQueue::ack` делает `queue.retain(...)`,
TTL-sweep — то же, выход процесса освобождает heap. Ни одна из операций
**не зануляет** байты: освобождённая память физически хранит ciphertext до
повторного использования аллокатором/ядром. Под моделью «RAM dump» (прямо в
§8) эти байты извлекаются. `zeroize` в зависимостях отсутствует.

Более того, «crypto-erasure» — это уничтожение **ключа**, после чего
ciphertext бесполезен. Реле **не владеет ключами сообщений вовсе** — значит
crypto-erasure выполняют клиентские ратчеты (Double Ratchet выбрасывает
message key после расшифровки). Реле в лучшем случае делает best-effort wipe
RAM, но не crypto-erasure. README приписывает релею то, чего он не делает.

**Как лучше:**

1. Честная формулировка: «реальная crypto-erasure — на клиентах (ратчет);
   реле лишь минимизирует время жизни ciphertext в RAM».
2. `zeroize::Zeroizing<Vec<u8>>` для буфера ciphertext, зануление при ACK и
   при TTL-sweep. В связке с `mlockall` (F1) это ограничивает экспозицию
   строго живой RAM на ≤ TTL.

## F3 (высокая). «Zero-knowledge relay» — сервер знает весь социальный граф

**Claim README/PR:** «zero-knowledge relay».

**Доказательство ложности.** Реле знает и может логировать/выдать под root:

- **Кто отправитель** — `POST /v1/messages` аутентифицирует отправителя
  подписью, привязывая `device_id` отправителя к каждому конверту
  (`api.rs`, `verify_request` в `send_message`).
- **Кто получатель** — поле `to` передаётся **открытым** `device_id`.
- **Членство и время вступления** — персистентный roster `devices.db`
  (device_id ↔ pubkey ↔ created_at).
- **Присутствие** — время connect/disconnect по каждому устройству (WS).
- **Размер** — длина ciphertext не padding'уется, утечка размера сообщения.

Итог: root-атакующий восстанавливает полный граф «кто↔кому↔когда↔как
часто↔какого размера». Это **знание**. Корректный термин — максимум
«zero-**content**-knowledge».

**Как лучше (доказуемо убирает конкретные рёбра графа):**

1. **Sealed sender.** Реле проверяет лишь *членство в группе* (анонимный
   или одноразовый delivery-token), не узнавая, **какой** участник отправил.
   Убирает ребро «отправитель→сообщение».
2. **Roster только в RAM** (F5) — убирает персистентный список членства с
   диска.
3. **Padding до фиксированных корзин** (напр. 4/16/64 KiB) — убирает
   size-корреляцию.
4. **Из логов убрать `device_id`** (F4) — убирает персистентный timeline
   присутствия.
5. Дальше — §18 документа (разделение ingress/relay/queue), но это post-MVP.

После (1)+(3)+(4) реле перестаёт быть узлом, из которого извлекается граф
общения; сейчас — извлекается тривиально.

## F4 (средняя). Логи пишут device_id → persistent timeline присутствия на диске

**Claim:** «privacy-preserving logging: только lifecycle-события»; §15
документа требует минимизировать логи.

**Доказательство.**

```
src/ws.rs:124:  tracing::info!(device_id = %device_id, "websocket connected");
src/ws.rs:162:  tracing::info!(device_id = %device_id, "websocket disconnected");
src/api.rs:91:  tracing::info!(device_id = %device.device_id, "device registered");
```

`device_id` в connect/disconnect на уровне `info` — это и есть метаданные
(кто когда онлайн). При стандартном journald они ложатся на диск и переживают
TTL сообщений. «Lifecycle-события» с идентификатором = timeline присутствия.

**Как лучше:** в steady-state логах не писать `device_id` вовсе (или
усечённый salted-hash, с сэмплированием и коротким retention); присутствие —
только на `debug`, выключенном в проде. Логировать факты («ws connected»),
не субъектов.

## F5 (средняя). devices.db на диске = список членства + время вступления

**Доказательство.** `registry.rs` хранит в SQLite `device_id, identity_pk,
created_at` на обычном диске. Публичные ключи не секрет, но **сам факт
членства и время вступления** — метаданные, выдаваемые disk-snapshot'ом.

**Как лучше:** (а) держать roster только в RAM, восстанавливая при старте из
admin-подписанного манифеста; либо (б) шифровать at-rest ключом оператора,
который на боксе не лежит (передаётся в env/при старте и mlock'ается); либо
(в) хранить salted-hash от device_id вместо самих id.

## F6 (высокая). Дефолтные лимиты OOM'ят рекомендованный VPS

**Доказательство арифметикой.** Дефолты (`config.rs`):
`max_devices=32`, `max_queue_per_device=512`, `max_body_bytes=65536`.

```
32 × 512 × 65536 байт = 1 073 741 824 = ровно 1.0 GiB
```

только «сырой» очереди, не считая транзиентных base64-строк при парсинге
(+~33 %) и накладных JSON/аллокатора. Пример конфигурации Njalla в самом
документе — **~1.5 GB RAM**. Один участник (или держатель утёкшего токена)
наполняет очереди до OOM-kill → отказ сервиса для всей группы.

**Как лучше:** дефолты под 1.5 GB бокс (напр. `max_devices=16`,
`max_queue_per_device=64`, `max_body_bytes=16384` ⇒ ~16 MiB); плюс
**глобальный бюджет RAM** с backpressure: считать суммарные байты в очередях
и отвечать `429`, когда превышен потолок, а не полагаться только на
per-device лимит.

---

## F7 (средняя). Нет rate limiting

Единственный гейт — invite-token + подпись. Нет ограничения частоты запросов
и числа соединений с IP. На 1.5 GB боксе это усиливает F6.

**Как лучше:** token-bucket на устройство, cap соединений на IP (tower-слой),
и/или лимиты на reverse-proxy; задокументировать как обязательный, не
опциональный, для этого класса железа.

---

## F8 (средняя). Модель invite-token: утечка = захват вступления + griefing device-limit

**Доказательство.** Один общий `MSGR_INVITE_TOKEN` на группу. Кто угодно с
токеном может зарегистрировать много **новых** ключей и выбрать все
`max_devices` слоты (F6) → легитимные участники получают
`device_limit_reached`. Registration-payload не содержит nonce/expiry
(`auth.rs:22`), так что защищает только duplicate-key.

**Как лучше:** одноразовые admin-подписанные инвайты (token = подпись над
nonce+expiry+квота устройств), отзыв, привязка инвайта к конкретному
устройству. Тогда утечка одного инвайта не рушит контроль вступления.

## Прочие находки (низкая severity, но реальные)

- **F9. Replay-cache в памяти** сбрасывается при рестарте → подписанный
  запрос можно повторить в окне ±300 с сразу после рестарта. Лучше: серверный
  monotonic-epoch в canonical-строке или персист high-water timestamp; либо
  сузить окно.
- **F10. Registration без freshness** — replay безвреден (duplicate-key), но
  для гигиены и связи с одноразовым инвайтом (F8) добавить expiry.
- **F11. Утечка размера** — частный случай F3, лечится padding'ом.
- **F12. Нет отзыва/ротации устройств** — скомпрометированное устройство
  остаётся в группе до ручного `DELETE` строки. Лучше: подписанный
  revocation-list, раздаваемый клиентам.
- **F13. Реле доверенно по доступности/цензуре.** Злонамеренное реле (а это
  ровно модель угроз) может молча дропать/переупорядочивать сообщения — E2EE
  это не ловит. Вне рамок конфиденциальности, но зафиксировать: клиентам
  нужен end-to-end ACK и порядковые счётчики ратчета, чтобы обнаруживать
  пропажу/переупорядочивание, не полагаясь на реле.

## Приоритеты исправления

| # | Находка | Severity | Ломает claim | Стоимость фикса |
|---|---------|----------|--------------|-----------------|
| F1 | swap/core-dump выносят данные на диск | Критично | «ничего на диск» | Низкая (mlock+rlimit+юнит) |
| F3 | полный metadata-граф | Высокая | «zero-knowledge» | Средняя (sealed sender+padding) |
| F6 | OOM на 1.5 GB VPS | Высокая | пригодность по железу | Низкая (дефолты+бюджет) |
| F2 | нет зануления RAM | Высокая | «crypto-erasure» | Низкая (zeroize+честный текст) |
| F4 | device_id в логах | Средняя | §15 / disk | Тривиальная |
| F5 | roster на диске | Средняя | disk-metadata | Средняя |
| F7 | нет rate limit | Средняя | availability | Низкая |
| F8 | invite-token модель | Средняя | контроль вступления | Средняя |

**Рекомендуемый порядок:** сначала «дешёвые, но ломающие заголовочный claim» —
F1, F4, F6, F2 (все правятся малым кодом/деплоем и systemd-юнитом), затем
metadata-блок F3/F5/F11 и модель инвайтов F8. F13 — фиксируется как требование
к клиенту, не к релею.

**Главный вывод аудита:** код честно защищает содержимое, но README продаёт
две гарантии, которых нет («ничего на диск», «zero-knowledge»), и дефолты не
соответствуют рекомендованному железу. До исправления F1/F2 формулировки в
README следует ослабить до фактического уровня, иначе документация вводит
пользователя в ложное чувство безопасности — что для security-продукта хуже,
чем честно названное ограничение.
