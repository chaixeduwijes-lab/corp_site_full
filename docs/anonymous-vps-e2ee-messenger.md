# Анонимный и независимый VPS/VM-хостинг для закрытого E2EE-мессенджера

## Цель

Найти независимый VPS/VM-хостинг, который максимально снижает объём идентифицирующих данных о владельце инфраструктуры и подходит для размещения backend закрытого E2EE-мессенджера на группу до 10 человек.

Важно разделять две задачи:

1. **Анонимность владельца VPS** — насколько мало данных хостер требует при регистрации и оплате.
2. **Конфиденциальность переписки** — способность сервера прочитать содержимое сообщений.

Даже максимально privacy-oriented VPS не должен быть доверенной стороной. Архитектура приложения должна быть такой, чтобы компрометация всей VM, базы данных, файловой системы и root-доступа не позволяла расшифровать переписку.

---

## 1. Рекомендуемый вариант — Njalla

### Почему Njalla

Njalla — privacy-oriented сервис, ориентированный на пользователей, которым важна минимизация передаваемых персональных данных.

Основные преимущества:

- для регистрации требуется минимум данных;
- можно использовать email или XMPP;
- не требуется стандартный KYC с паспортом;
- поддерживается оплата Monero;
- доступны VPS с root-доступом;
- инфраструктура ориентирована на собственные серверы и собственную сеть;
- компания позиционирует себя как privacy-focused провайдер.

Для небольшого backend нашего мессенджера ресурсов начального VPS достаточно с большим запасом.

Пример базовой конфигурации:

- 1 CPU core;
- около 1.5 GB RAM;
- около 15 GB storage;
- лимит трафика порядка 1.5 TB.

Для проекта максимум на 10 участников этого более чем достаточно.

### Плюсы

- минимум регистрационных данных;
- Monero;
- независимая privacy-oriented модель;
- VPS с полноценным root;
- хороший вариант для небольшой приватной инфраструктуры;
- нет необходимости использовать аккаунт крупного американского cloud-провайдера.

### Минусы

- цена выше самых дешёвых VPS;
- сама VPS не является trusted execution environment;
- администратор физической инфраструктуры теоретически контролирует hypervisor;
- сетевые метаданные полностью исчезнуть не могут.

### Вывод

Основной кандидат для backend проекта.

Сайт: <https://njal.la/servers/>

## 4. SporeStack

SporeStack интересен максимально минималистичной регистрацией.

Особенности:

- может не требовать email;
- token-based access;
- поддержка Tor;
- оплата Monero;
- privacy-first модель.

Но есть существенный архитектурный нюанс: часть VM может размещаться на инфраструктуре сторонних cloud-провайдеров. Это снижает независимость цепочки.

### Плюсы

- очень сильная модель no-KYC;
- можно использовать Tor;
- Monero;
- минимум идентифицирующих данных.

### Минусы

- зависимость от инфраструктуры сторонних VPS/cloud-провайдеров;
- меньше контроля над всей цепочкой инфраструктуры.

### Вывод

Хороший вариант, если основная цель — минимальная регистрационная идентификация.

Для критерия «максимально независимый хостинг» Njalla предпочтительнее.

## 6. Что не рекомендуется для этой задачи

Для обычных бизнес-проектов следующие платформы отличные:

- AWS;
- Azure;
- Google Cloud;
- DigitalOcean;
- Hetzner;
- OVH.

Но если основная цель — минимизация идентифицирующих данных и независимая privacy-oriented инфраструктура, я бы не ставил их на первое место.

Причина не в качестве серверов. Причина в другой модели:

- более тесная связка аккаунта с платёжными реквизитами;
- крупная корпоративная инфраструктура;
- больше систем telemetry/accounting;
- зачастую больше данных вокруг аккаунта.

## 7. Рекомендуемая схема для нашего мессенджера

Вариант: **Njalla VPS + E2EE backend**

Backend выполняет только:

- приём encrypted envelope;
- временное хранение ciphertext;
- доставку;
- ACK;
- удаление после доставки или TTL;
- хранение публичных ключей;
- device authentication.

Backend НЕ хранит:

- plaintext сообщений;
- E2EE private keys;
- message keys;
- chain keys;
- local vault keys;
- PIN пользователей.

---

## 8. Критический принцип

Сервер нужно проектировать так, будто завтра произойдёт следующее:

> атакующий получает root VPS, disk snapshot, RAM dump, database, logs, TLS certificate и исходный код backend.

Даже после этого он не должен получить возможность восстановить историю сообщений.

Это намного важнее выбора конкретного VPS-провайдера.

---

## 9. E2EE должен работать поверх VPS

Правильная схема:

```text
Телефон Alice
    |
    | plaintext существует только здесь
    |
    | E2EE encryption
    v
Ciphertext
    |
    | TLS
    v
VPS
    |
    | VPS видит только ciphertext
    v
Ciphertext
    |
    | TLS
    v
Телефон Bob
    |
    | E2EE decryption
    v
Plaintext
```

VPS не должен иметь ключа расшифровки.

---

## 10. Не хранить историю на VPS

Предлагаемая политика:

```text
message arrives
      |
      v
encrypted queue
      |
      +--> recipient online
      |       |
      |       v
      |     delivery
      |       |
      |       v
      |      ACK
      |       |
      |       v
      |     DELETE
      |
      +--> recipient offline
              |
              v
          TTL <= 20 min
              |
              v
            DELETE
```

Таким образом VPS используется как временный relay, а не как архив сообщений.

---

## 11. Удаление должно быть криптографическим

Обычный:

```sql
DELETE FROM messages;
```

не гарантирует физического исчезновения данных с SSD.

Поэтому безопасность должна строиться на **crypto-erasure**.

После того как message key уничтожен, старый ciphertext должен стать бесполезным.

---

## 12. Оплата

Если используется privacy-oriented payment model, предпочтительнее избегать привязки VM к обычной банковской карте.

Поддержка Monero у privacy-oriented хостера уменьшает количество платёжных метаданных, передаваемых самому хостеру.

Однако это не делает пользователя «магически анонимным».

Следует отдельно учитывать:

- IP при регистрации;
- IP администрирования;
- email;
- DNS;
- domain registration;
- SSH access;
- blockchain/payment metadata;
- локальное устройство администратора.

---

## 13. Administration

Для проекта создать отдельный SSH key.

Например:

```text
messenger-prod-ed25519
```

Не использовать тот же SSH private key, которым администрируются остальные серверы.

Private key:

- не передавать на сервер;
- не хранить в Git;
- не отправлять в Telegram/email;
- хранить только на доверенном административном устройстве.

---

## 14. Server hardening

Минимальный production baseline:

- Linux;
- SSH keys only;
- `PasswordAuthentication no`;
- `PermitRootLogin no`;
- firewall;
- automatic security updates;
- application под отдельным UNIX user;
- TLS 1.3;
- минимум открытых портов;
- no control panel;
- no phpMyAdmin;
- no unnecessary services.

Открыть наружу только необходимое. Например:

```text
22/tcp  SSH — желательно дополнительно ограничить
443/tcp HTTPS / WSS
```

Если SSH можно закрыть через VPN/admin overlay — ещё лучше.

---

## 15. Логи

Минимизировать server logs.

Не писать:

```text
message text
ciphertext
Authorization
private keys
invite token
push token
PIN
```

По возможности ограничить срок хранения:

- access logs;
- system logs;
- authentication logs.

Но не ломать operational security ради полного отсутствия логирования. Нужен разумный баланс.

---

## 16. Domain name

Для первой версии domain name вообще необязателен. Можно использовать отдельный hostname либо серверное имя.

Если используется домен:

- не привязывать его к основной корпоративной инфраструктуре;
- использовать отдельный registrar/account;
- включить DNSSEC, если архитектура это позволяет;
- не размещать публичный сайт на том же backend.

---

## 17. Важный риск — hypervisor

Ни Njalla, ни FlokiNET, ни любой другой обычный VPS не дают математической гарантии того, что оператор hypervisor не может наблюдать состояние работающей VM.

Это фундаментальная особенность VPS.

Поэтому: **не хранить ключи расшифровки сообщений на VPS вообще**.

Тогда даже потенциальный доступ host-оператора к VM значительно меньше влияет на confidentiality содержимого переписки.

---

## 18. Ещё более сильный вариант

Если позднее потребуется повысить независимость от VPS-провайдера:

```text
Device
  |
 E2EE
  |
Relay A
  |
Relay B
  |
Recipient
```

Можно разделить:

- публичный ingress;
- message relay;
- storage queue.

Тогда один сервер получает меньше полной metadata картины.

Но для группы из 10 человек это усложнение не требуется для MVP. Сначала нужен качественный E2EE.

---

## 19. Рекомендуемое решение

Для первой production-версии:

**Infrastructure** — Njalla VPS.

**Backend** — Rust:

- axum;
- tokio;
- rustls;
- SQLite/PostgreSQL;
- WebSocket.

**Message storage** — только ciphertext. TTL: до 20 минут или до ACK — что раньше.

**Keys** — все E2EE private keys только на пользовательских устройствах.

**Administration** — отдельный SSH key.

**Logging** — минимальный privacy-preserving режим.

**Backup** — не делать backup временной очереди сообщений.

## 20. Итог

Если выбирать один сервис для нашего текущего проекта: **Njalla**.

Причина:

- privacy-oriented модель;
- минимум регистрационных данных;
- поддержка Monero;
- VPS/root;
- высокая степень инфраструктурной независимости;
- подходит по масштабу;
- нет необходимости использовать hyperscaler.

Второй кандидат: **FlokiNET**, особенно VPS в Исландии.

При этом главный security requirement остаётся неизменным:

> **Мы не доверяем VPS содержимое переписки вообще.**

Даже полностью скомпрометированный сервер должен содержать только зашифрованные данные, из которых невозможно получить plaintext без ключей пользовательских устройств.
